# Research: Product Platform Foundation

## 1. Authoritative database

**Decision**: Use PostgreSQL 16 as the authoritative operational database for local development, test integration, and deployment.

**Rationale**: The product needs shared durable records, transactions, constraints, backup/restore tooling, and a path beyond the current process-local and SQLite demo stores. PostgreSQL is already required by Constitution 2.0.0. Version 16 is mature, widely supported, and sufficient for the MVP.

**Alternatives considered**: MySQL contradicts the approved constitution; SQLite cannot be the shared multi-user production source of truth; databases per capability add unnecessary MVP complexity.

## 2. Python persistence stack

**Decision**: Use SQLAlchemy 2 with the synchronous psycopg 3 dialect (`postgresql+psycopg://`) and short transaction-scoped sessions.

**Rationale**: Existing FastAPI endpoints and services are synchronous. This avoids an unrelated async rewrite while providing transactions and typed models. SQLAlchemy documents both sync and async psycopg 3 operation: <https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#psycopg>.

**Alternatives considered**: async SQLAlchemy/asyncpg forces broad changes; raw psycopg duplicates mapping; psycopg2 is older than the selected driver.

## 3. Code-first schema evolution

**Decision**: SQLAlchemy declarative models define schema intent; Alembic owns all production initialization and upgrades. Production code never calls `metadata.create_all()`.

**Rationale**: Alembic records ordered revisions and supports reviewed forward/downgrade scripts. Its documentation states autogenerated migrations are candidates requiring manual review: <https://alembic.sqlalchemy.org/en/latest/autogenerate.html>.

**Alternatives considered**: startup `create_all()` cannot safely express upgrades; hand SQL duplicates model intent; automatic production startup migration is unsafe under concurrent startup.

## 4. Architecture migration strategy

**Decision**: Use a modular monolith with capability modules and a strangler migration beside the current `routers`, `schemas`, and `services`.

**Rationale**: One deployment and transaction boundary stay simple while each tested move is reviewable and reversible.

**Alternatives considered**: a big-bang rewrite risks regressions; microservices add operational complexity; generic service folders do not solve ownership.

## 5. First persistence pilot

**Decision**: Port `acceptance_records` and `shadow_observations` first behind a `PlanningEvidenceRepository` port while preserving public endpoints.

**Rationale**: They are durable, tested, and exercise JSONB, idempotency, timestamps, ordering, and readiness without pulling later user/trip work forward.

**Alternatives considered**: expenses belong to increment 008; user/trip tables belong to 006/007; moving every store is too broad.

## 6. Legacy SQLite handling

**Decision**: Provide an explicit idempotent importer from `BE/data/accepted_plans.db`; never read SQLite silently in production mode.

**Rationale**: Existing evidence is preserved without two authoritative stores. A source fingerprint prevents duplicate imports.

**Alternatives considered**: permanent dual-write causes reconciliation risk; deletion loses evidence; startup import hides an operational action.

## 7. Configuration and modes

**Decision**: Use `pydantic-settings` with explicit `APP_MODE=demo|production|test`, `DATABASE_URL`, allowed origins, snapshot settings, and optional providers.

**Rationale**: Typed validation fails safely before traffic. Demo is explicit and production database absence makes readiness fail.

**Alternatives considered**: the custom parser lacks typed validation; multiple config files increase drift.

## 8. Health, errors, and diagnostics

**Decision**: Preserve `/v1/health` as liveness, add `/v1/ready`, propagate `X-Correlation-ID`, and standardize safe errors.

**Rationale**: Required data/schema failures must block readiness, optional providers must not block the product, and local diagnostics must work without external observability.

**Alternatives considered**: one health endpoint conflates liveness/readiness; external tracing is unnecessary now.

## 9. Flutter foundation

**Decision**: Keep `ChangeNotifier` and existing dependencies. Move only cross-cutting API configuration, safe errors, and correlation propagation into `FE/lib/core`.

**Rationale**: The UI works. Replacing state management creates broad churn unrelated to foundation work.

**Alternatives considered**: Riverpod/BLoC can be revisited later; leaving cross-cutting code top-level obscures ownership.

## 10. Local operations and backup

**Decision**: Provide PostgreSQL in `compose.yaml`, also support external PostgreSQL through `DATABASE_URL`, document DBeaver values, and use `pg_dump`/`pg_restore` with a checksum manifest.

**Rationale**: Compose gives a repeatable default without forcing it on deployments. PostgreSQL documents its logical archive workflow: <https://www.postgresql.org/docs/current/backup-dump.html>.

**Alternatives considered**: committed dumps violate runtime-data rules; custom exports are less reliable; Docker-only excludes existing installations.
